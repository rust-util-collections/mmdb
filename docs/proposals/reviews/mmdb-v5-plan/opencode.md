**Scope and method.** I read the plan, then checked the MMDB sources and tests it cites at `8aacd0f`. Verdict: the ordering (1–3 independently landable, 4 profiled before 5) and the separation of committed work from experimental changes are sound, and units 1 and 2 have real, falsifiable completions. The plan's weaknesses are concentrated in unit 1 (wrong stated error classification, tests that cannot observe state) and in units 4–5 (an executable profile that cannot produce the promised tables, plus latency evidence that will not survive inspection).

## Ranked edits

**1. Fix the stated classification before testing it, and make the L0 gate observable.**
Plan §1 (test command `cargo +stable test --test integration test_write_options_no_slowdown`).

The plan says the change keeps ordinary write classification `InvalidArgument` and "Document the two transient conditions"; the existing `docs/usage.md` (quoted verbatim at the top of §1) already states that the L0 slowdown-threshold path "returns `InvalidArgument`" — so the prose at line 31 would have the implementer contradict the doc they cite at line 41. It also says `ErrorKind::Busy` matches `FlushQueue::check_capacity`, which it does, but the L0 `no_slowdown` branch currently fires *before* `check_capacity` would return `Busy` in any configuration where `l0_slowdown_trigger <= l0_stop_trigger` (both are checked from the same `l0_count`). In that window the L0 branch is the only error this method produces, and changing it to `Busy` changes the first error a caller at a slow L0 queue sees.

*Hypothesis:* with `l0_slowdown_trigger = 3`, `l0_compaction_trigger = 3`, three files present, `no_slowdown = true` returns `Busy`; the same call with `no_slowdown = false` succeeds after the queue drains; `ErrorKind::InvalidArgument` is returned only for a malformed batch (`WriteBatch::new()` with a bad prefix, checked in `src/types.rs:474`) and for invalid open options.

*Baseline/control:* the current test at `tests/integration.rs:780` asserts `InvalidArgument` and therefore *must* be edited to `Busy`; run it against the unmodified tree first to confirm it passes on the old contract, then against the new code. For the write-group neighbor claim, the baseline is the existing group path at `src/db.rs:3093`–`3113`, which already returns `Busy` per-request for `no_slowdown` batches — a good predictor, not evidence.

*Procedure:* three explicit flushes; read the WAL file length in `dir` (directory + `"{:06}.wal"` using the open `wal_number` from `db.inner.lock()`) and `db.read.current_sequence()` before and after the rejected call; `assert_eq!(db.get(b"blocked").unwrap(), None)`; `db.flush()`; retry; `db.close()`; reopen. Repeat with a worker parked via the existing `pause_next_flush`/`sync_wal` hooks already used at `src/db/flush.rs:416` and `:526`, and with the second trigger (`check_capacity` → `Busy("immutable memtable queue is full")`).

*Pass/fail:* both triggers produce `Busy`; WAL bytes and sequence are byte-identical around the rejection; the neighbor's `Ok(())` lands only after the retryable queue drains; the retryable variant is reproducible at least 5/5 runs (it is, today, single-threaded — no concurrency is introduced). **Defer** unit 1's second sentence (stop-threshold case, test at `src/db.rs:5935`–`5980`) until the L0 gate is `Busy`, because its stop path is under a write-queue lock and is not the same invariant. Separately, `check_capacity` returns `Busy` only after `p.submitted - p.durable >= limit` is observed from a *durable* submission, which the documented `Busy` at `usage.md` already matches.

**2. Give unit 2 an observable criterion and remove the unobservable steps.**
Plan §2, `BlockCachePool::entry_count` (`src/cache/block_cache.rs:296`).

The completion evidence ("A two-member test reconciles the reported bytes…") is the right shape, but three of the listed checks cannot pass as written: (a) `block-cache-usage` is *entry count* (`src/db.rs:2099` documents it; `BlockCache::entry_count` at `:617` = `pool.entry_count() + pins`), so "compare weighted bytes" requires either a new pool-level `weight_bytes()` or a documented definition of "bytes" that includes pinned `value.data.len()` — the current `weigher` charges `value.data.capacity().max(1)` (`:247`), i.e. allocator capacity, not `len`, so a test that expects `sum(len)` will fail; (b) the plan says "Check zero capacity" — at capacity 0 `disabled = true` and `:404` `insert_entry` returns immediately, so no measurement can show anything except zero, which is a vacuous check and should be stated as "returns exactly zero and never reads the stores"; (c) "Park the oldest flush, observe immutable bytes, release it and check the gauge falls after durable install" requires an immutable-bytes property that `get_property` does not expose (`src/db.rs:2075` has no such key) and that `SuperVersion::immutable_memtables` is a `Vec<Arc<MemTable>>` with no `approximate_size` sum helper, so this must be added, not awaited.

*Hypothesis:* for a two-member shared pool at capacity C, after `run_pending_tasks()` and with pins released, `sum over members of `pool.segmented_weight + overflow_weight` ≤ C` and, for a single member's normal/overflow block, the pooled value equals the sum of `entry.value.data.capacity()`.

*Procedure:* keep the existing wrong-data guard (`tests/shared_cache.rs:31`) and add (i) `pool.weight_bytes()` gated behind `test-utils` returning `inner.weighted_bytes()` + `overflow.weighted_bytes()`, (ii) a `DB` property `stats.immutable-bytes` summed over one pinned `SuperVersion` using `MemTable::approximate_size`, read outside the timed loop as the plan already says; assert membership: insert 1 MiB, freeze at `write_buffer_size` below 1 MiB, check immutable bytes rise by ≤ 1 MiB + slack, park via `pause_next_flush` (already used at `src/db/flush.rs:416`), release, and assert the gauge falls only after `flush()` installs. Reuse the parking hooks already in the tree.

*Pass/fail:* both bounds hold at exactly zero and at over-segment weights, with `l0`-file-number aliasing covered by the existing `shared_cache` namespacing test. **Do not** test gauge decay against the timeline of `submit` → `durable`; that is the one place a timing-based assert will flake. **Defer** the aggregate-cap eviction experiment, which is correctly called separate but is currently 4/8/12-file dependent and needs its own unit.

**3. Correct the export and reopen claims so they are testable against a real v4 shard.**
Plan §3, "Export" paragraph, and the self-test command `cargo +stable test --manifest-path tools/v4-export/Cargo.toml`.

The existing `golden.rs` reads `tests/fixtures/v4.3.15` and exports with `args(["3", "2"])`, i.e. 3 levels and **two-byte** prefix. The plan's required case is an **eight-byte** prefix, and the export path does not force the caller's prefix: `tools/v4-export/src/main.rs:66–72` passes `prefix_len` from the CLI through to both v4 and v5 opens, so an 8-byte prefix test is possible but must pass the flag, and the plan should say so — otherwise a "verified" case silently tests 2-byte prefixes. More important is the **writable-reopen geometry** claim: `main.rs:74` opens the destination with `with_num_levels(levels.clamp(2, 16)).with_prefix_len(prefix)` and never re-checks the persisted geometry; a `destination_reopened_writable` test must assert `num_levels == 3` and `prefix_len == 8` survive reopen (`DB::open_read_only` adopts the MANIFEST header per `src/db.rs:794`), because the exported store's `CURRENT` is whatever `v5::DB::open` wrote at ingest, not what the CLI passed. The plan's "preserve a destination created by a competing publisher" is already covered at `tools/v4-export/src/main.rs` `publish` and `tests/src`-level `publication_preserves_existing_directories_and_can_be_retried` (in `tools/v4-export/src/main.rs` `#[cfg(test)]`), but the `golden.rs:44` destination-absent test only proves the *failed scan* case; it does not prove that the rename path preserves an existing destination — add that as a separate assertion against `publish`, not as an export failure.

*Hypothesis:* for a shard with 8-byte prefix and 3 levels, the exported `dst/CURRENT` opens writable, `db.put` succeeds, `db.close()` and reopen returns the new rows, and an invalid destination geometry (pass `["17", "8"]` to force an out-of-range level and check the CLI rejects) fails at parse, not at publish.

*Procedure:* copy `tests/fixtures/v4.3.15` to a temp dir, append a WAL record for a key with an 8-byte key, run the binary with `["3", "8"]`, compare `collect::<Vec<_>>()` plus `iter.error()` (already the pattern at `golden.rs:31`), reopen with `DB::open_read_only` and then writable `DB::open`, and inspect `db.get_property("num-files-at-level0")` for the 3-level expectation. For the writable-geometry check, assert the reopen path with `prefix_len = 2` on an 8-byte prefix store fails `InvalidArgument` (or succeeds only if the store's MANIFEST records 8 — record which, because it is a contract decision).

**4. Replace the named-but-absent benchmark basis and set the unit-4 threshold from a pre-registered plan budget, not from a post-hoc number.**
Plan §4 and its self-test block, and the §5 `W + A → max(W, A)` claim.

The §4 table describes a large workload (16 DBs, 3 switchable immutable limits, 10k-operation workers) that `benches/v5_profile.rs` does not implement: it is a single-DB, 4-thread, fixed-`KEYS` = 32,768 loop with one 128-byte value, one write-buffer size and one `max_immutable_memtables` read from env (`benches/v5_profile.rs:18–31`), and the self-test's `for depth in 1 2 4` loop only varies one knob. It also reports `read` and `write` p99 and p999 *per thread after merging all workers' samples*, so the printed p99 is a mixture of two different op classes, not the "per-operation-class throughput and p99" the table promises. The §5 `W + A → max(W, A)` statement has no baseline measurement attached and no stated expected effect size; as a planning statement it is fine, as a performance claim it is unsupported.

*Procedure:* before implementing anything, run the existing profile once per depth in a fresh process with a fixed seed, a read-only warm-up and a single-writer control as the plan already says, and record `VmHWM` with the `cat` the existing code prints (`benches/v5_profile.rs:70`). Pre-register, in the plan, a decision budget for unit 5: adopt `W + A → max(W, A)` only if the measured candidate median is below `baseline_median − k · spread` for `k = 2` of 5 interleaved pairs, *and* `throughput` does not drop, *and* peak RSS does not grow by more than 5% at the 16-DB arm. State `k` and the 5% as a **planning budget** with the rationale (small enough to absorb process noise on a single x86_64 host, large enough to reject a change that costs tail latency for a mean gain) and mark it non-empirical until measured. For §4's per-operation table, first fix `benches/v5_profile.rs` to report `read` and `write` from separately-owned vectors and to record `input bytes`, `batch entries`, `queue wait` and `wakeups` — the queue-wait instrument does not exist and `src/db.rs` has no exposed per-group wait counter, so this is a build, not a run.

*Defer* any statement about L0 parallelism thresholds "4/8/12" in §5 until `tests/compaction`/leveled thresholds are read out; I did not verify those numbers in the sources, and the plan presents them as fact.

**Most important change before implementation.** Change §1's classification and its prose in `docs/usage.md` first, because it is the only item whose defect is in the *plan's own text* and whose stated contract contradicts the cited source; fixing the prose after the code has landed leaves a two-codebase inconsistency in the compatibility surface the VSDB adapter will read. Specific ordering: edit `docs/usage.md:108` and `docs/usage.md:110` together with `tests/integration.rs:804` (the old `InvalidArgument` assertion) so the contract is frozen before `src/db.rs:2904` is touched, then make the L0 check return `Busy` with a message that names the threshold, then extend the test.
